# Playwright Скилл: Автоматическое тестирование MVP «Пигмалион»

## 🎯 Назначение и Контекст
Этот скилл наделяет Qwen способностью автономно запускать браузер, тестировать логику приложения Pygmalion (К.Р.И.С.Т.А.Л.Л.) и исправлять найденные баги в коде (например, в `App.jsx`). 
* Окружение: Локальное React-приложение.
* Хранилище: Состояние хранится исключительно в `localStorage` (ключи: `ro_dag`, `crystal_state`, `ue_timer`, `acts_log`). Бэкенд не требуется.

## 🧠 Фундаментальные принципы (Канон)
1. Тестируй поведение и смысл, а не просто реализацию кнопок.
2. Интерфейс (UI) — это лишь отражение. Источником истины всегда является `localStorage`.
3. **Критическое ограничение (Constraint):** Это НЕ финансовая логика. ЗАПРЕЩЕНО интерпретировать У.М. (R.M.) как крипто-токен, валюту, финансовый актив или инструмент для спекуляций. Это протокол нематериального следа и признания.
4. **Смысловой разрыв сущностей (У.Е. ≠ У.М.):** У.Е. (R.U.) не подлежит передаче после трансформации. У.М. (R.M.) не эквивалентен У.Е. Они принадлежат к абсолютно разным смысловым слоям (временный импульс vs постоянный след).

## 🎭 Сценарии тестирования (4 Акта)

### Акт 1 — Эмиссия (Создание У.Е. / R.U.)
* **Цель:** Убедиться, что пользователь может создать ежедневные У.Е.
* **Шаги:** Открыть приложение -> Триггер создания У.Е. -> Проверить появление У.Е. в UI.
* **Ожидание в localStorage:** У.Е. существует только как локальный временный импульс. Никаких постоянных записей в реестре не создается.

### Акт 2 — Передача (Назначение)
* **Цель:** Проверка корректной передачи У.Е. получателю.
* **Шаги:** Выбор получателя -> Отправка У.Е. -> Проверка состояния "в ожидании" (pending).
* **Ожидание в localStorage:** У.Е. помечается как "pending" и записывается с таймстемпом. Активируется окно осмысления.

### Акт 3 — Окно отзыва и «Окно осмысления»
* **Цель:** Проверка права на отзыв У.Е. в течение ограниченного окна осмысления (настраивается, по умолчанию ~24–28 часов).
* **Шаги:** Имитация отзыва внутри окна / Имитация отзыва после закрытия окна.
* **Ожидание в localStorage:** Отзывается не след, а завершённость акта. У.М. не создается, но факт попытки передачи сохраняется как след (в `acts_log`). Попытка отзыва *после* истечения окна осмысления должна завершаться отказом.

### Акт 4 — Финализация (Трансформация У.Е. → У.М.)
* **Цель:** Проверка превращения импульса в постоянный след в системе.
* **Шаги:** Отправка У.Е. -> Имитация истечения окна осмысления -> Перезагрузка приложения.
* **Ожидание в localStorage:** У.Е. необратимо трансформируется в У.М. В реестре `ro.DAG` создается постоянная запись, содержащая: отправителя, получателя и таймстемп. Запись не может быть удалена или изменена.

### Сценарий Споров (Dispute)
* **Цель:** Проверка механизма оспаривания при несовпадении ожиданий.
* **Шаги:** Имитация спора по транзакции.
* **Ожидание в localStorage:** Спор НЕ изменяет оригинальный след. Вместо смены статуса, спор создает новый, связанный след (linked trace) во втором слое реестра `ro.DAG`.

## 🛠 Правила автоматизации и отладки для Qwen
1. Всегда запускай браузер через Playwright. Используй реальные клики и вводы (никаких моков).
2. После каждого действия валидируй состояние: `await page.evaluate(() => localStorage.getItem("ro_dag"))`.
3. Если тест падает (FAIL), найди несоответствие между UI и `localStorage` в файлах проекта (например, `App.jsx`).
4. Внедри минимальный фикс в код и автоматически перезапусти тест.

## 📋 Формат вывода
Каждый прогон тестов должен возвращать в терминал:
* Название Акта и выполненные шаги.
* Результат: **PASS / FAIL**.
* Обнаруженная проблема (если есть).
* Предложенный и внедренный фикс на уровне кода.

// Базовый шаблон теста
import { test, expect } from '@playwright/test';

test('Act 4 — RU → RM finalization', async ({ page }) => {
  await page.goto('http://localhost:3000');

  // отправка У.Е.
  await page.click('[data-testid="send-ru"]');

  // проверка localStorage
  const roDag = await page.evaluate(() =>
    JSON.parse(localStorage.getItem('ro_dag'))
  );

  expect(roDag.length).toBeGreaterThan(0);
});
